# ambrogio-app

Repository del backend Ambrogio con modello ingegneristico Reqvire dedicato. Ambrogio è pensato come assistente domestico open source con [licenza MIT](LICENSE), installabile nel proprio homelab. Le ulteriori scelte sull'organizzazione del codice applicativo saranno definite in base alle capability del prodotto.

## Struttura

- `system-model/`: modello Reqvire del backend. Le cartelle `Capabilities/`, `Requirements/`, `Contracts/`, `Verifications/` e `Thesaurus/` facilitano la consultazione; il tipo degli elementi e le relazioni Reqvire ne definiscono il significato. Le ontologie e i contratti semantici, quando necessari, appartengono a `Ontologies/`.
- `AGENTS.md`: istruzioni per gli agenti, metodo e strumenti di lavoro.

Il sito e la documentazione utente appartengono a repository separati.

## Stato del progetto

Questo repository contiene il backend della conversazione familiare e il suo modello Reqvire. Il client terminale è sviluppato nel repository separato `ambrogio-cli`, che possiede il proprio modello; integra il backend tramite il contratto HTTP pubblico. SQLite e Kysely sono scelti per l'archivio delle conversazioni; il server usa TypeScript ESM, compilato con `tsc`, Node.js 24 o successivo e Fastify per l'API HTTP; pnpm gestisce il workspace del backend. Le applicazioni eseguibili risiedono in `apps/` e i moduli business in `packages/`. I flussi testuali e vocali del server appartengono al modulo business «Conversazioni», con codice Domain e Application rispettivamente in `src/domain/` e `src/application/` del package. Gli adapter per componenti tecnici esterni integrati in «Conversazioni» risiederanno nel package, in `src/adapters/in/` o `src/adapters/out/` secondo il loro ruolo; quelli che collegano due moduli business risiederanno nell'app che li assembla, in `src/adapters/out/<consumer>-to-<provider>/`. I package business non importano altri package business, app o package tecnici condivisi del workspace, neppure tramite `import type`; i collegamenti tra moduli avvengono nelle app. I test di ciascun modulo business risiedono nel suo package; le prove della collaborazione tra moduli risiedono nell'app che li assembla. I test Domain importano codice di produzione solo dal Domain del proprio modulo; i test Application solo dall'Application e dal Domain dello stesso modulo, anche per gli `import type`. I test degli adapter inbound importano codice di produzione solo dal proprio adapter e dall'Application, senza Domain; quelli degli adapter outbound solo dal proprio adapter, dall'Application e dal Domain, senza adapter inbound. Il confine vale anche per gli `import type`. Ogni package business espone tramite `package.json` solo subpath espliciti di Application e degli adapter necessari alle app, senza export della radice, wildcard o Domain; le app importano solo tramite tali subpath, senza accedere ai file interni. I package generici di condivisione, come `shared`, `common`, `utils` o `domain-kit`, richiedono una nuova decisione architetturale esplicita nel modello Reqvire. Domain e Application restano indipendenti da Node.js e dalle dipendenze npm runtime; le integrazioni tecniche passano attraverso porte Application e adapter. La composition root dell'applicazione server sceglie e fornisce le implementazioni delle porte. Nelle app, `src/runtime/` contiene i meccanismi tecnici del processo, `src/composition/` le scelte di assemblaggio dei componenti e gli entrypoint coordinano l'esecuzione. Ogni conversazione conservata, avviata dalla chat testuale o dalla voce, può essere riaperta e continuata tramite un client della chat testuale. Ogni nuova interazione vocale apre una nuova conversazione. Il client della chat testuale invia il turno con `POST /api/conversations/turns` e riceve sulla stessa richiesta un UI Message Stream v1 di AI SDK in formato SSE (`text/event-stream`), con header `x-vercel-ai-ui-message-stream: v1`. Il corpo JSON della richiesta usa `text` per il nuovo turno e `conversationId` quando si continua una conversazione; il server recupera lo storico dall’archivio. La parte iniziale `start` comunica `conversationId` e `turnId` in `messageMetadata`, anche quando si continua una conversazione. Le parti `text-start`, `text-delta` e `text-end` trasportano il testo progressivo. Il successo è confermato soltanto dalla parte `finish` con `finishReason: "stop"` e `messageMetadata.turnStatus: "answered"`, emessa dopo la conservazione dell’esito. La sola chiusura del flusso o il marcatore di trasporto `[DONE]` non attestano il successo. Dopo l’accettazione del turno, il backend completa l’elaborazione e conserva l’esito anche se il client si disconnette. Se la conversazione viene consultata mentre il turno è ancora in corso, lo storico segnala il turno «In elaborazione». Alla nuova consultazione, lo storico mostra l’esito conservato se disponibile. La riapertura non crea una seconda connessione SSE e non recupera frammenti parziali. Se si verifica un errore dopo l’avvio del flusso, una parte `error` contiene il messaggio pubblico sicuro in `errorText` e il flusso si chiude senza la conferma di successo. Se erano già stati emessi frammenti testuali, lo scambio conserva l’esito di errore e il messaggio pubblico, senza registrare i frammenti come risposta completata. Gli errori determinati prima dell’invio degli header SSE usano invece una risposta HTTP `4xx` o `5xx` con corpo JSON `error`, come esito del turno. Un turno con `text` vuoto o composto solo da spazi bianchi produce `400` senza modificare l’archivio, anche se `conversationId` è inesistente; con testo valido, un `conversationId` inesistente produce `404` senza creare una nuova conversazione. Gli import di Domain restano nel proprio Domain e quelli di Application nel proprio Application o Domain, inclusi gli `import type`. Nel server, i rifiuti previsti di Domain, Application e porte sono valori di esito distinguibili dal successo; guasti tecnici inattesi e bug si propagano come eccezioni fino al confine che li gestisce. Le nuove eccezioni costruite dal server per guasti tecnici non tradotti o bug sono oggetti `Error`. Un layer che non aggiunge contesto propaga il guasto originale; un `catch` con contesto operativo crea un nuovo `Error` con messaggio del componente e `cause` identica al valore catturato, senza modificarlo. Il messaggio di guasto per la famiglia è costruito separatamente dalla diagnosi tecnica e non espone cause, stack, messaggi tecnici del provider o il valore originale dell'eccezione. Il componente che decide l'esito esterno possiede l'eventuale log diagnostico definitivo e ne emette al massimo uno per guasto; i componenti intermedi che propagano il guasto non lo registrano di nuovo come errore definitivo. Domain e casi d'uso Application non dipendono da un logger; la diagnostica dei guasti inattesi spetta ai componenti tecnici che li gestiscono. Rifiuti previsti, errori di protocollo previsti e guasti tecnici tradotti in esiti previsti non generano automaticamente log dedicati `warn` o `error`. Quando un guasto inatteso, un bug o un valore lanciato sconosciuto raggiunge il fallback pubblico HTTP e il canale diagnostico è disponibile, il confine emette un solo log definitivo di livello `error`. Nel log definitivo, il campo strutturato `err` contiene l'oggetto `Error` con la catena `cause` in memoria; la riga JSON include una rappresentazione serializzata di `err`. La vista JSON usa soli campi ammessi esplicitamente: include lo stack degli `Error` del progetto e usa una descrizione costante sicura per errori esterni o valori sconosciuti, senza copiarne messaggio, stack o proprietà aggiuntive. La serializzazione non modifica gli oggetti Error originali né la loro catena cause mantenuta in memoria. Il confine HTTP che gestisce definitivamente un guasto normalizza una sola volta il valore catturato: conserva la stessa istanza se è un Error, altrimenti crea un Error con messaggio diagnostico fisso e cause identica al valore originale, senza convertirlo in stringa. Il runtime HTTP usa Pino per eventi tecnici JSON, uno per riga, e scrive per impostazione predefinita su stdout; raccolta e inoltro verso un eventuale backend di log sono responsabilità del deployment, senza integrazione diretta nel codice applicativo. Il runtime HTTP non emette i log automatici di ricezione e risposta di Fastify; gli eventi diagnostici HTTP contengono soltanto campi scelti esplicitamente, senza acquisire automaticamente oggetti di ingresso, uscita o contesto. Ogni evento diagnostico include un campo event con un nome stabile dichiarato nel punto di emissione. Il confine HTTP genera un correlationId UUID v4 distinto per richiesta, lo include nei relativi log e lo restituisce come X-Request-Id in ogni risposta gestita, anche di errore;  Il logger e le integrazioni HTTP non acquisiscono automaticamente testi delle conversazioni, corpi o header HTTP, input o output dei casi d'uso e credenziali. Ogni caso d'uso con rifiuti previsti dichiara nel proprio contratto Application un insieme chiuso dei soli rifiuti osservabili dal chiamante, senza un catalogo globale condiviso. Casi d'uso e porte con rifiuti previsti restituiscono `Result<T, E>` nelle firme TypeScript, eventualmente in `Promise`, con `E` pari alle varianti dichiarate nel rispettivo contratto. Ogni modulo business che usa `Result<T, E>` lo definisce localmente come `Readonly<{ ok: true; value: T }> | Readonly<{ ok: false; error: E }>`. I casi d'uso gestiscono ogni rifiuto previsto delle porte e traducono quelli bloccanti, tramite mapping espliciti, in varianti proprie con tipi nominati distinti da quelli delle porte. Ogni variante di rifiuto previsto è un tipo nominato `Readonly` con `kind` letterale distinto nella propria unione; le varianti non sono classi e non si distinguono con `instanceof`. Oltre a `kind`, le varianti contengono solo eventuali campi specifici tipizzati, stabili e necessari al chiamante, senza campi generici comuni obbligatori. I mapping esaustivi usano uno `switch` su `kind`, un ramo per variante e un `default` che chiama `assertNever` sul valore completo; il server compila con TypeScript `strict`. Per un caso d'uso con rifiuti previsti, firma callable, factory e unione dei rifiuti osservabili sono nello stesso file `<use-case>.use-case.ts`. Gli adapter inbound rappresentano gli esiti usando solo le varianti pubbliche Application del caso d'uso, ne gestiscono tutta l'unione e non dipendono dai tipi di rifiuto interni delle porte o del Domain. Ogni componente configurabile del server usa un file JSON locale dedicato, separato da quelli degli altri componenti. I file effettivi restano fuori da Git e dalle immagini container; eventuali esempi nel repository sono privi di credenziali effettive. Le credenziali delle API esterne sono lette dal file JSON locale effettivo del rispettivo componente. Nell'MVP Ambrogio non implementa account o autenticazione applicativa: il deployment limita l'accesso ai client ammessi dall'installatore tramite rete e, se presente, reverse proxy. Il server sarà distribuito come immagine Docker eseguibile senza Docker Compose; un eventuale file Compose sarà solo un esempio di avvio. La suite automatica del backend userà Vitest. Il resto dell'organizzazione del codice e le altre scelte tecnologiche devono ancora essere definiti; il modulo «Conversazioni» è in implementazione incrementale.

Seguire [AGENTS.md](AGENTS.md) per la sequenza di lavoro e usare la [documentazione ufficiale Reqvire](https://reqvire.org/) come riferimento autorevole.

## Decisioni successive

L'interazione vocale è facoltativa: la chat testuale funziona senza la sua configurazione. L'arresto ordinato ferma l'accettazione di nuovi turni, interrompe quelli attivi senza attenderne la risposta e ne conserva lo stato «Interrotto» prima di chiudere l'archivio. Dopo una terminazione improvvisa, i turni accettati rimasti senza esito sono riconosciuti come «Interrotto» al riavvio e non vengono ripetuti automaticamente. Le migrazioni SQLite sono applicate prima dell'attivazione degli ingressi. L'elenco delle conversazioni è paginato e ordinato per ultima attività, dalla più recente.

Il server legge all'avvio i JSON locali dei soli componenti attivi, senza sovrascriverne i valori tramite variabili d'ambiente. La configurazione richiesta viene validata prima di attivare le risorse; i componenti ricevono solo i valori pertinenti già convertiti. Un JSON mancante o invalido blocca l'ingresso interessato con un errore sicuro.

L'osservabilità iniziale usa log tecnici JSON strutturati e identificativi di correlazione per richiesta HTTP. Metriche, tracing distribuito e audit separati non sono introdotti nella prima versione; richiederanno una decisione e verifiche proprie se emergerà un'esigenza concreta.

L'API HTTP autorizza CORS solo per origini esplicitamente configurate nel JSON del componente HTTP; senza elenco non autorizza origini. Le rotte che ricevono un corpo applicano un limite positivo esplicito e rispondono con `413` a un corpo troppo grande prima di avviare il caso d'uso. Le risposte che trasportano dati conversazionali, inclusi elenco, storico e flussi SSE, inviano `Cache-Control: no-store`.

Gli header di sicurezza dell'API HTTP sono applicati globalmente con `@fastify/helmet`, comprese le risposte di errore, con eventuali deroghe motivate per rotta. HSTS è attivo solo quando la configurazione validata dichiara che l'origine pubblica usa HTTPS; non si attivano implicitamente `includeSubDomains` o `preload`.

Il server dispone di prove Vitest, comprese prove degli adapter di persistenza su SQLite reale. Dalla radice del repository si eseguono `npm test`, `npm run build` e `npm run typecheck`; il modello si controlla con Reqvire `validate` e `lint`. I test che aprono listener HTTP locali richiedono un ambiente che consenta l’ascolto su `127.0.0.1`.

Durante l'elaborazione o la risposta a un turno, tutti i client dell'installazione disabilitano l'invio di nuovi turni testuali e vocali. Il server rifiuta i turni concorrenti da qualsiasi ingresso e conversazione senza conservarli; la richiesta HTTP testuale riceve `409` con un messaggio JSON sicuro, prima di SSE. Nessun turno viene accettato per essere elaborato più tardi: se non può partire subito, viene rifiutato senza finire in coda.

L'ingresso HTTP verifica forma e decodifica dei propri dati prima del caso d'uso; per la forma delle richieste conversazionali usa schemi TypeBox con Fastify/Ajv, senza coercizione dei tipi, valori predefiniti impliciti o rimozione dei campi aggiuntivi. Application coordina le precondizioni che dipendono dal contesto della conversazione; Domain garantisce stati e transizioni del singolo turno, mentre SQLite garantisce atomicamente l'unico turno attivo nell'installazione. Un controllo preliminare non sostituisce la garanzia atomica dell'archivio.

Nella prima versione non si conservano eventi di dominio per consegne successive e non si usano outbox o code per pubblicarli. Gli eventi di dominio locali non sono introdotti ora; restano un'opzione se un caso d'uso concreto ne avrà bisogno.

Nel modulo «Conversazioni», i casi d'uso ricevono input e producono dati di successo definiti in Application, indipendenti da HTTP e voce; gli adapter traducono i dati nei rispettivi formati. Le porte Application prendono il nome dalla capacità richiesta dal caso d'uso, senza nomi di prodotti, protocolli o librerie delle implementazioni. Operazioni e dati delle porte esprimono il bisogno del modulo; gli adapter traducono verso le API e i tipi dei fornitori esterni. Le porte a oggetto con metodi nominati usano `interface` TypeScript; dati, unioni e contratti callable usano `type`.

L'archivio delle conversazioni espone ad Application un contratto di scrittura dedicato alle transizioni del turno e contratti di lettura separati per storico ed elenco. Il contratto di scrittura può usare il salvataggio coerente della conversazione come aggregato oppure operazioni di transizione esplicite; non impone un'interfaccia CRUD universale. Le transizioni di ammissione e chiusura di un turno aggiornano atomicamente stato del turno e occupazione dell'installazione con transazioni SQLite brevi; chiamate esterne e streaming avvengono fuori dalle transazioni. L'adapter classifica gli esiti SQLite secondo la postcondizione della singola operazione: zero righe non indica da solo successo o rifiuto, e guasti o risultati ambigui non vengono presentati come rifiuti previsti. Il server possiede e chiude la risorsa SQLite/Kysely tramite la composition root; gli adapter ne ricevono solo l'accesso necessario. Gli adapter convertono esplicitamente i dati tra righe SQLite e valori Domain o proiezioni Application, preservandone il significato senza imporre una forma unica ai mapper. Domain garantisce le transizioni valide del singolo turno; l'archivio garantisce l'unico turno attivo nell'installazione. Il testo di un turno accettato viene conservato com'è stato ricevuto: gli spazi iniziali e finali sono ignorati solo per verificarne la vuotezza.

Conversazioni e turni ricevono UUID v4 generati tramite una capacità fornita ad Application dalla composition root, prima della creazione dello stato Domain. L'archivio conserva gli identificativi e ne garantisce l'unicità persistente; l'ordinamento dello storico non dipende dagli UUID. I casi d'uso ottengono l'ora corrente da un orologio fornito dalla composition root e passano gli istanti al Domain; gli istanti storici restano invariati dopo il caricamento. Nel codice Application e Domain gli istanti sono `Date` validi; gli oggetti Domain ne fanno copie difensive in ingresso e in uscita. SQLite conserva gli istanti come interi di millisecondi Unix, convertiti esplicitamente dall'adapter di persistenza senza perdita di precisione.

Ogni richiesta di una pagina dell'elenco legge lo stato corrente dell'archivio; i client possono ripartire dalla prima pagina per aggiornare la consultazione.

La dimensione massima delle pagine e la rappresentazione della continuazione sono definite nel contratto HTTP dell'elenco.

## Ingresso HTTP di consultazione

La tranche eseguibile attuale espone `GET /api/conversations` e `GET /api/conversations/:conversationId`. `POST /api/conversations/turns` resta disponibile come adapter e nei test, ma non è registrato in questo processo finché non viene scelto un produttore concreto delle risposte.

Il processo richiede due file JSON locali, esterni al repository. Un esempio di configurazione HTTP è:

```json
{"host":"127.0.0.1","port":3000,"allowedOrigins":[],"publicHttps":false}
```

`host` e `port` sono obbligatori. `allowedOrigins` è facoltativo e, se assente, non autorizza origini CORS. Per un'origine pubblica esclusivamente HTTPS, impostare `publicHttps` a `true` e fornire `hstsMaxAgeSeconds` positivo. Un esempio del JSON Conversazioni è:

```json
{"archivePath":"/percorso/locale/conversations.sqlite","listPageSize":20,"maxListPageSize":100,"language":"it"}
```

Per questo ingresso `archivePath` è obbligatorio; gli altri campi conservano i valori predefiniti già definiti nel modello. Dopo la build, avviare il processo indicando solo i percorsi dei file:

```bash
pnpm build
AMBROGIO_HTTP_CONFIG_PATH=/percorso/locale/http.json \
AMBROGIO_CONVERSATIONS_CONFIG_PATH=/percorso/locale/conversations.json \
node apps/server/dist/main.js
```

## Immagine Docker del backend

Il [Dockerfile](Dockerfile) costruisce il server con Debian e Node.js 24 in due fasi. I file JSON effettivi e l'archivio SQLite sono forniti tramite mount esterni; non entrano nel contesto copiato nell'immagine. Docker Compose non è richiesto.

La prova ripetibile è `node scripts/verify-docker-image.mjs`. Esegue `docker build` e `docker run` senza Compose, monta JSON di prova e una directory SQLite esterna, verifica che tali file non siano presenti nell'immagine, richiede `GET /api/conversations` con Node e controlla la creazione dell'archivio nel mount. Il 16 ottobre 2026 la prova è passata: HTTP `200`, archivio esterno creato; l'immagine locale risultante è `sha256:9a79d8e48cfe5b14a3b03f157d05716be9616ce779bd9e64dd22d0cd9f41d941`.

## Reqvire locale

La versione usata per il modello iniziale è Reqvire `1.3.2`. Dalla radice del repository:

```bash
npx -y @reqvire-org/reqvire@1.3.2 --workspace "$PWD" validate
npx -y @reqvire-org/reqvire@1.3.2 --workspace "$PWD" mcp --port 8082 --enable-mutations
```

Il secondo comando avvia in primo piano il server MCP. La [configurazione Codex del progetto](.codex/config.toml) punta a `http://127.0.0.1:8082/mcp`. Per le mutazioni Reqvire richiede un branch con almeno un commit e un worktree pulito. Dopo aver avviato il server, aprire una nuova sessione Codex per rendere disponibili i suoi strumenti; fermare il server prima di modificare il modello con editor o CLI.

Per aprire l'Explorer web in un altro terminale:

```bash
npx -y @reqvire-org/reqvire@1.3.2 --workspace "$PWD" serve --port 8080
```

La UI è disponibile su `http://127.0.0.1:8080`. Il comando avvia solo l'Explorer; il server MCP configurato per Codex rimane sulla porta 8082.
